Kineva — Workouts tab proposal

A survey of the Workouts tab as it ships today, what it does well, where it falls short, and a proposal in three mockups: a set ledger in the session where every set of every movement takes real reps and weight (assistance included), a hub in the Halo idiom, and an exercise page with history and records. Then the data model and a phased build plan. All numbers are test data for one lifter on Monday 7 September.

The tab is the "Building the Monolith" program hub: Jim Wendler's 6-week 5/3/1 size template, iOS only. Screens below are the real build on the iPhone 17 Pro simulator with a seeded cycle (TMs 315 / 225 / 365 / 135 lb). References were pulled from Mobbin and are linked under each concept.

What is there today

The tab is one program. Without a cycle it is a single card asking for training maxes. With one, the hub shows the next session as a hero, an 18-workout progress ring, the six-week ledger, the training maxes and recent history. A session is a guided screen: one movement at a time, the current set as a big weight × reps, plate math, a dock with the timer and a "Complete set" button, then the next movement. Assistance movements are a rep target (100 chins) with EMOM and a "log reps" cluster. A weight pad edits the bar weight; a hidden adjuster records partial reps. The session saves to Apple Health and logs the Apple Music soundtrack. The old heart-rate workout list (WorkoutsView) is no longer a tab; it is only reachable from a Today card.

Keep as is. The program engine and its tables, autoregulation (week review, Friday relief, TM steering), plate math, the weight pad with the "override carries to later sets" rule, rest and EMOM timers, spoken cues, Apple Health save, the Music log, the live activity, CSV export, archives. None of this is in question; the proposal builds on the same MonolithStore.
The core gap, and what you asked for. A set is a checkbox. "Complete set 1" records the prescribed 220 × 5; what you actually lifted only enters through side doors: a weight pad for the bar, a hidden adjuster for partial reps, an AMRAP count on the last set. Assistance work is a total ("34 / 100 reps") and the per-set logger with reps and weight only appears while an EMOM is running. There is no way to add an exercise the program did not prescribe, and nothing outside the program can be logged as a lift at all.

Gaps, ranked

#GapWhere it bites
1No per-set reps and weight for main lifts. The row is done or not.Any set where the bar or the reps differed from the plan. History and e1RM are built on what the plan said, not what happened.
2Assistance sets with reps and weight can only be logged during an EMOM.Chins, dips, face pulls, curls, DB rows: most lifters log a set, rest, log a set. Weighted or assisted variants have nowhere to record the load.
3No way to add an exercise to a day.Extra accessory work (a second pull, carries, ab work) is invisible.
4No strength logging outside the program.A deload week, a gym day between cycles, or a friend's session: the tab has no home for it.
5No exercise history, records or e1RM."What did I squat last Monday?" needs the CSV export. TM review is the only progression read.
6Set logs live in one UserDefaults JSON blob.Not in the SQLite store, not in .noopbak backups, not queryable, iOS-only with no Android twin.
7The hub is program chrome, not a workout tab.Heart-rate sessions from the strap, walks, runs and detected activities are on another screen. Effort from lifting and from cardio never meet.
8Session screen hides the day.One movement at a time is calm, but the whole day's sets, the "previous" reference and the running volume are out of view.

Concept 1 · Session

Set ledger — every set takes real reps and real load

The movement card becomes a table: set number, what you did last time, load, reps, and a check. The next set is pre-filled from the plan (or from your last session for assistance and extras), so the fast path is still one tap on "Log set". Tapping a field opens a keypad sheet that edits both numbers at once; the load field has four modes: bar weight, bodyweight, added weight (+25 lb on chins) and assisted (−50 lb on a machine or band). The same table serves the main lifts, the assistance movements and anything you add with "Extra exercise", so there is one way to log a set in the whole app.

What this changes

  • The set is the unit of record: reps, load, load mode, time, RPE (optional). Achieved reps and partials stop being a hidden adjuster.
  • Assistance logs per set without an EMOM. The rep target stays as a running total in the header; EMOM stays as an option, not the gate.
  • "Extra exercise" adds any movement to the day from a small library (with free text), gets the same ledger, and counts toward volume.
  • The dock keeps the timer, rest countdown, running volume and the one big button. The "Previous" column is the reference the current screen lacks.
  • The weight pad's rules survive: a changed bar weight carries to later sets of the same movement; plate math sits under the keypad.

Concept 2 · Hub

Hub — today's session, this week, your lifts, everything recent

Same rules as Pulse and Night: one screen, lean, every row a door. Today's session is the hero with its top sets and an estimate. The week is three rows. The four lifts show an estimated 1RM from logged sets (Epley on the best set) with a four-week delta. Recent lists lifting sessions, strap cardio, detected activities and freestyle days in one place, each with its Effort. The program chrome (ledger, TMs, reviews, archives) moves behind one row.

What this changes

  • "＋" starts a freestyle strength session (no program), adds a manual workout, or opens the HR live session. The heart-rate workout list folds back into this tab.
  • Lift tiles replace the training-max card as the first read of progress. TMs stay one tap in.
  • A cycle-less state still shows Recent and Lifts, so the tab is useful before and between cycles.

Concept 3 · Exercise page

Exercise page — records and history from what you actually logged

Every lift tile, every movement header and every history row opens this. The hero is an estimated 1RM over time with the training max as the dashed baseline, so the "TM at 85–90% of true max" rule is visible rather than remembered. Under it, best set, best load, session count and volume, then the history as one line per session with the AMRAP or partial in bold and a PR chip when a set beat every earlier one at that rep count.

What this changes

  • e1RM, PRs and volume are computed from the set ledger, in StrandAnalytics, with tests. They exist for assistance and extras too (best chins set, total dips this cycle).
  • The metric lab gets e1rm_squat, lift_volume and assist_reps series so lifting can be overlaid with HRV, sleep and Charge like anything else.
  • The week review's TM steering reads the same ledger instead of the plan-with-flags.

Data model

Today every set lives inside MonolithSessionRecord as flags and dictionaries (done, amrapReps, partialReps, weightOverrides, assistSets), persisted as one JSON blob in UserDefaults. That is fine for program state (which week, which day, the TMs, the reviews) and wrong for the sets: they are the history, they belong in the store, in backups, and on both platforms.

TableColumnsNotes
liftSessiondeviceId · startTs (PK) · endTs · kind (program / freestyle) · programKey (w1d1 or null) · title · notes · exertion · workoutStartTs (the strap HR session it overlaps, if any)One row per lifting session. Links to the existing workout row so Effort, HR and the session live together.
liftSetdeviceId · sessionStartTs · exerciseId · setIndex (PK) · reps · loadKg · loadMode (bar / bodyweight / added / assisted) · plannedReps · plannedLoadKg · kind (ramp / top / amrap / widowmaker / assist / extra) · rpe · completedAtThe unit of record. Load is stored in kg to one decimal, shown in the session's unit. Assisted load is negative in the ledger math and positive here with the mode set, so nothing is ambiguous.
exerciseid (PK, stable slug) · name · category (barbell / dumbbell / bodyweight / machine / cable / other) · liftKey (squat / bench / deadlift / press or null) · isCustomSeeded with the program's movements plus a small library (~60). Custom rows are the user's own names. Ids never change once shipped.
  • Migration. One GRDB migration, v43-lift-sets, with a pinned schema test, and its Room twin in the same PR so the schema is byte-identical even before Android has a screen for it. The existing Monolith blob is migrated once on launch: every done set becomes a liftSet row with the plan values and any override or partial applied. The blob keeps program state only.
  • Backup. The three tables join the .noopbak whitelist. Only Int, Double and String cross the wire.
  • Analytics. StrengthMath in StrandAnalytics: Epley e1RM, PR detection per rep count, session and per-exercise volume, with the oracle test in Kotlin.
  • Assisted work. "Assistance" in the program sense (chins, dips, face pulls, curls, rows) gets the ledger like everything else. "Assisted" in the load sense (band or machine taking weight off) is the fourth load mode, so a −50 lb assisted chin and a +25 lb weighted chin are both a set of chins on the same page, and the e1RM math ignores assisted sets.

Decisions I would like from you

  • RPE. Optional field on the keypad sheet, off by default, or leave it out entirely? The autoregulation could use it later.
  • Exercise library size. The program's movements plus about 60 common lifts, or the program's plus free text only?
  • Freestyle sessions. In build 3 as proposed, or pulled forward into build 1 so a non-program gym day can be logged sooner?
  • Assisted mode. Needed now (machine or band assistance), or is "+ Added" and bodyweight enough for your assistance work?
